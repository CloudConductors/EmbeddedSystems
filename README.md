# Smart Maintenance Embedded Systems
Please note, this software cannot be run without an Arduino listening on COM3. Any attempts of making this software multiplatform failed. However, this README will provide details on the functionality of this program.

## Introduction
The Smart Maintenance capstone project focuses on combining the “internet of things” (IoT) and artificial intelligence to analyze collected sensor data to predict anomalies and create maintenance schedules. The embedded systems portion of this project focuses on the generation, collection, processing, and transmission of sensor data. 

Unfortunately, due to the nature of embedded systems, not all software that was created for this project can be run locally on a personal computer. This project utilizes Arduino microcontrollers to generate realistic component data, and transmit the data to another program that processes it. Certain features of the Arduino, such as serial communication, could not be easily emulated within the given time frame.

This document’s main purpose is to showcase the functionality of the embedded system’s portion of this project. It will highlight key features of the software written for the Arduino, as well as the software written for an intermediary computer, such as a Raspberry Pi.

## Data Generation
Due to limitations of the Arduino microcontroller available at the time, data from our dataset could not be stored on the device. Instead, data is generated using normal distribution.

The Arduino microcontroller is responsible for determining the simulated component’s probability of failure, and generating the realistic data that is sent to the Raspberry Pi. This data is sent to the Raspberry Pi using a serial connection to the board.

To generate the data, the mean and standard deviation of both good and bad data were recorded using a simple Python program. These values are then used to generate realistic random values. The Arduino also determines if the component will fail on the current iteration using normal distribution. 

The randomly generated values are sent to the Raspberry Pi as a JSON string.

## Reading Data
Data that is generated by the Arduino will be read and processed by the Raspberry Pi. The Raspberry Pi is responsible for collecting data, running anomaly detection on the data, and sending the data to AWS.

To read data sent by the Arduino, the Raspberry Pi continually checks the Arduino’s serial port. If data is received, the Raspberry Pi will append a timestamp before continuing.

## AWS
After receiving data from the Arduino, the Raspberry Pi sends all collected data to a DynamoDB table stored in an AWS server. This allows other applications to access the data, without needing access to the Raspberry Pi or Arduino.

To lower overall costs, collected data sent in batches to AWS. To achieve this, data is written to a batch file until the batch exceeds a certain threshold. Once this threshold is reached, the program uses AWS’ built-in batch feature to send data in bulk.

The batching process can be overridden by the anomaly detection process. The anomaly detection feature also updates another DynamoDB table, responsible for holding maintenance schedules.

## Anomaly Detection
Once data is received from the Arduino, the Raspberry Pi is responsible for running an anomaly detection machine learning model on the data. This model is first downloaded from an AWS S3 bucket, and then is stored locally on the machine for future uses. Downloading the model at the start of the application ensures that the most up-to-date version of the model is being used.

If an anomaly is detected, the program performs a series of steps. The first step is to update the schedule table on DynamoDB to show that the train requires maintenance. The next step is to bypass the batching system and send all data regardless of the current batch size, ensuring that the most up-to-date information is available to the user.

## Network Outage Caching
Due to the importance of the data being collected and handled by the application, a caching feature was added to ensure that data is collected and processed, even without a network connection. When connection is restored, the data is then processed and sent accordingly. 

There are several network checks implemented in key areas throughout the application. The first check is done when downloading the model from the AWS S3 bucket. If there is not a network connection established, the application checks for a model stored locally. 

The next check is during the main event loop of the application. If there is a network outage, the application still collects and stores data in a batch file. However, anomaly detection cannot be completed due to the need to connect to AWS. 

Once the connection is restored, the application runs the anomaly detection model on every entry stored in the batch file, ensuring that any anomaly that occurred during the outage is properly reported.
